Fitness Diet Reviewer

An ASP.NET Core app where people plan a weekly diet and fitness instructors review it, upgraded from my Master’s project into a live, tested, production-ready app.

My own project, not client work. Demo data only. Source code available on request.

  • C#
  • ASP.NET Core 8 MVC
  • SignalR
  • Identity with roles
  • Entity Framework Core
  • MySQL and SQLite
  • xUnit
  • GitHub Actions
  • IIS

The starting point

I built the first version in 2024 as my diploma project at UNWE: users, instructors and administrators, a weekly meal table, and instructor guidelines. In 2026 I went back to it the way I would approach a client’s legacy app: read the code, find what is broken or unsafe, fix it with tests, then make it pleasant to use.

What I fixed first: security

A review of my own code found five access-control and injection problems. Each one now has an integration test that fails on the old code and passes on the new.

  • Any signed-in user could open, edit or delete someone else’s meals by changing the id in the address. Meals are now always looked up inside the signed-in user’s own diet.
  • Any user could change another user’s profile. Now only the owner or an administrator can.
  • Instructor names and guideline text were written into pages unescaped, so a name like <script> would run in other people’s browsers. They are encoded now.
  • Editing foods and approving food requests only checked that someone was signed in. They now require the Administrator role.
  • Promoting, demoting and deleting users worked from a plain link. They now need a POST with an anti-forgery token, like every other change.

On top of that: sign-in lockout after five wrong passwords, security headers, friendly 403, 404 and 500 pages, and package updates that leave no known vulnerable dependencies.

Then: a live interface

The old diet page was a static table that reloaded for every change. Now it is a board backed by a small JSON API.

  • Add, edit and remove meals in a dialog, without reloading the page; a removed meal can be undone
  • Food search as you type, with calories and macros for the amount shown before you save
  • Day totals, target bars and weekly averages update with every change
  • SignalR pushes changes to everyone who has the diet open: an instructor sees when a user asks for feedback, and the user sees a new guideline the moment it is written
  • On a phone the board shows one day at a time, picked with day tabs

Under the hood

One place for the nutrition math. Calories and targets were copied across several views, and one copy added already-rounded numbers. A single service now does it: macros per gram, day totals summed before rounding, and daily targets from the revised Harris-Benedict formula with activity factors. Unit tests pin the numbers.

Runs anywhere in one command. Locally it uses SQLite with seeded demo users; production stays on MySQL, chosen by configuration. The database context no longer reads its own settings file, so tests and hosting configure it the same way.

Ready for IIS. A PowerShell script publishes the app, creates a no-managed-code app pool and site, gives the pool write access only to its data folder, and waits for the health check. Data protection keys live on disk, so sign-ins survive an app pool recycle.

Testing

28 automated tests: unit tests for the nutrition math, and integration tests that start the real app on a throwaway database, sign in over HTTP and check the API, the anti-forgery rules, each security fix, and a real SignalR connection. GitHub Actions runs them on every push.

How it was made

The original version is my own diploma work. For the 2026 upgrade I worked with AI coding tools and reviewed every change: the security review, the API and live board, the tests and the redesign.
